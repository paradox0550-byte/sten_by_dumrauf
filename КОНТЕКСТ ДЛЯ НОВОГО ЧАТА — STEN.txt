## 1. Главные правила работы

- Проверять фактическое состояние main и PR, а не доверять предположениям.
- Не выдавать непроверенное за готовое.
- Не мерджить PR без явного разрешения Александра.
- Один PR = одна понятная задача.
- Перед PR: typecheck, lint, tests, build.
- Backend, API Gateway, Cloud Function, Lockbox и deployment не менять в frontend-задачах без явного разрешения.
- Визуальные проверки в реальном браузере выполняет человек; GitHub/Codex не считаются заменой browser QA.
- Не использовать mock/random/fake production data.
- Missing != zero: отсутствующие данные остаются null.
- Расчёт выполняется до интерпретации AI.
- Для финансовых расчётов должен быть понятен источник и формула.
- Если требование конфликтует с реальным кодом, сначала сообщить о конфликте и предложить безопасное решение.

## 2. Продуктовая модель

STEN должен помогать руководителю пройти цепочку:
revenue → COGS → payroll → OPEX → EBITDA → net profit → analytics → actions.

Ключевой принцип: Data over decoration.

Роли и контекст:
- руководитель операций;
- несколько ресторанов/проектов/филиалов;
- Scope: период → проект → branch → restaurant → department;
- отделы, не относящиеся к выбранному branch, нельзя сравнивать с ним.

## 6. Finance / P&L

Формулы:
- revenue = hall + delivery;
- food cost norm 25–35%;
- personnel = salaries + KPI;
- OPEX: rent/utilities/marketing/repair/household;
- OPEX norm: 3.0% до 2.5m revenue, 2.9% выше;
- EBITDA = revenue − cost − OPEX;
- net = EBITDA − depreciation − interest − taxes.

Метрики:
- avg check;
- turnover;
- delivery share;
- cancellations;
- ABC по sales qty/revenue/profit/food cost%;
- OLAP plan/fact by category/location.

P&L colour logic:
- favourable expense negative → green;
- unfavourable expense positive → red;
- revenue negative → red.

## 9. Auth / multi-tenancy

Направление продукта:
- email + password registration confirmation;
- либо login + password + organization ID;
- создание organization ID — только admin.

Главный принцип:
- контексты организаций изолированы;
- нельзя показать финансовые/сменные данные другого ресторана;
- Telegram profile/context не должен обходить organization boundary.

Не менять auth/backend только ради визуальной задачи.

## 12. Lessons

Известные проблемы:
- TS1005 может быть вызван синтаксическим повреждением при copy-paste;
- TS2322 unknown нужно сужать типами, не any;
- Yandex API Gateway не поддерживает YAML anchors — options нужно разворачивать;
- OpenAPI 3.0 exclusiveMinimum — boolean;
- Unicode quotes / zero-width characters могут ломать код;
- browser QA нельзя объявлять выполненным по одному CI;
- "+N/-0" вместо ожидаемого отката — повод проверить diff;
- frontend CI не должен менять backend;
- секреты нельзя помещать в чат/репозиторий; при утечке нужна ротация.

## 13. Перед началом нового задания

1. Проверить main.
2. Проверить актуальные открытые PR, если задача касается текущей очереди.
3. Найти фактический код, а не угадывать путь.
4. Зафиксировать scope.
5. Сделать минимальный PR.
6. Запустить проверки.
7. Проверить diff/stat.
8. Отдельно отметить, что CI доказал, а что требует ручной проверки.
9. Не merge без явного разрешения.
