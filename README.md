# Smart Tracking & Economic Navigator (STEN) — личный рабочий кабинет

**Персональный B2B-интерфейс для управления ресторанным бизнесом.**

Дашборд · P&L · аналитика · финансы · бюджет · команда · документы · STEN

Проект предназначен для собственного рабочего использования. Это не публичный SaaS и не социальный продукт: интерфейс сфокусирован на управлении бизнесом, финансовом контроле и операционных решениях.

В приложении нет email-регистрации, логина/пароля, восстановления пароля и лишнего аккаунтного UX. Доступ открывается персональным кодом.

## 2. Авторизация

Старый вход по 4-значному персональному коду **временно припаркован**.

Сейчас перепроверяется новый контур доступа:

1. email;
2. пароль;
3. подтверждение email;
4. организация / membership;
5. серверный JWT и проверка активного доступа.

POST /auth/unlock не является активным маршрутом и не должен возвращаться в production.

Офлайн-оболочка **не является авторизацией**.

Без действительного серверного JWT приложение:

- не создаёт synthetic user;
- не подменяет облачные данные;
- не выдаёт доступ к защищённым данным.

## 3. AI-контур

Пользовательский интерфейс показывает **STEN**, а не внутреннюю инфраструктуру AI.

Backend в Yandex Cloud обращается к Yandex AI Studio и YandexGPT.

Рекомендуемый model URI:

`gpt://<folder_id>/yandexgpt/latest`

Правила безопасности:

- AI credentials не попадают во frontend;
- model URI не должен попадать во frontend bundle;
- браузер обращается только к API Gateway;
- frontend использует `VITE_API_URL`;
- внутренние endpoint'ы и сетевые адреса backend не раскрываются клиенту.

---

## 4. STEN — рабочий AI-контур

STEN предназначен не для свободной беседы, а для управленческих задач:

- анализ P&L;
- сравнение плана и факта;
- поиск финансовых отклонений;
- анализ загруженных документов;
- подготовка плана действий;
- вопросы по операционным процессам;
- извлечение информации из документов;
- работа с PDF, DOCX, XLSX, CSV, TXT, MD, JSON и изображениями;
- read-only предпросмотр извлечённого содержимого перед управленческим анализом.

### Принцип достоверности

**Факты → расчётный контур → интерпретация.**

Модель не должна заменять источник данных.

Отсутствующий факт нельзя превращать в утверждение, а отсутствующее значение — в фиктивный ноль.

Расчётные показатели должны формироваться расчётным кодом. AI используется для интерпретации, объяснения и подготовки управленческих действий.

---

## 5. Документы

STEN поддерживает загрузку рабочих документов.

Ограничения frontend:

- максимум **15 МБ на файл**;
- передача через API Gateway;
- обработка существующим backend/storage-контуром;
- извлечённое содержимое может быть предварительно просмотрено до анализа.

Удаление локального кэша в настройках **не удаляет документы из облачного хранилища**.

## 6. Настройки и персонализация

В настройках доступны:

- **Профиль** — персональная информация рабочего контура;
- **Внешний вид** — светлая, тёмная или системная тема;
- **Рабочие блоки** — временное скрытие ненужных разделов;
- **Справка** — инструкция и FAQ.

Скрытие блока не удаляет его.

Кнопка **«Вернуть все»** восстанавливает исходную навигацию.

### UX-контракт модальных окон

Безопасные модальные окна должны поддерживать:

- явную кнопку `X`;
- закрытие по `Escape`;
- закрытие по клику вне окна, если действие не является опасным или необратимым.

## 7. Offline / PWA

Приложение использует Service Worker и кэширует:

- application shell;
- статические ресурсы;
- ранее загруженные ресурсы.

Это позволяет открыть уже установленный кабинет при временном отсутствии интернета.

Офлайн **не означает доступ к облачным данным**.

При отсутствии сети приложение должно:

1. сохранить рабочую оболочку;
2. сохранить доступные локальные данные;
3. не подделывать результат API-запроса;
4. выполнить сетевую операцию после восстановления связи.

## 9. CI/CD и production deploy

GitHub Actions отвечает за проверку и публикацию frontend.

Backend source и artifact также проходят проверки CI, однако публикация новой версии Cloud Function должна выполняться через отдельный защищённый Yandex Cloud deploy-контур с соответствующим service credential.

### Frontend pipeline

1. Checkout `main`.
2. Node.js 22.
3. `npm ci`.
4. TypeScript typecheck.
5. Lint.
6. Tests.
7. `npm run build`.
8. Копирование `index.html` в `404.html` для SPA-маршрутов.
9. Загрузка frontend в корень `smenavkarmane-business`.
10. Установка корректных MIME types.
11. Production smoke-проверка.

Frontend workflow **не должен иметь права на изменение Cloud Function**.

Доступ к Object Storage и доступ к Serverless Functions разделены намеренно.

До подключения отдельного backend deploy credential CI не должен имитировать успешный deploy Cloud Function.

## 10. Production smoke-check

После deploy необходимо проверить:

- главная страница открывается;
- прямой переход на `/unlock` не даёт пустой экран;
- CSS действительно применяется;
- JavaScript отдаётся как `text/javascript` / `application/javascript`;
- форма входа не выполняет обычный browser navigation на `/unlock`;
- `POST /auth/unlock` уходит именно в API Gateway;
- CORS разрешает `Content-Type`, `Authorization` и `X-Request-ID`;
- после успешного входа открывается dashboard;
- STEN отвечает через `/ask`;
- документы отображаются после загрузки;
- при отключении сети уже открытый кабинет не превращается в пустую страницу.

**Mock-данные не должны выглядеть как реальные показатели бизнеса.**

## 12. Security boundary

В frontend запрещено добавлять:

- DB credentials;
- JWT secret;
- AI credentials;
- внутренние VPC IP;
- backend source;
- `.env` с секретами;
- `node_modules`;
- `dist` в Git;
- старые email/password формы;
- фиктивные показатели, выдаваемые за реальные;
- Ollama/Qwen/local model runtime.

Также запрещено возвращать фиктивный UI секретаря до появления реальных backend endpoints для calendar/events/reminders/booking.

Спецификация:

`docs/SECRETARY_REFERRER_SPEC.md`

Секретарь — детерминированный контур и **не является вторым STEN**. GPT/YandexGPT не должен использоваться как скрытая замена его контрактной логике.

## 14. Визуальная система

STEN должен оставаться **спокойным, современным и премиальным B2B-интерфейсом**.

Основные принципы:

- минимум визуального шума;
- чёткая иерархия;
- компактные рабочие блоки;
- единая типографика;
- последовательная система spacing;
- полноценная светлая и тёмная темы;
- отсутствие декоративного glassmorphism;
- высокая читаемость финансовых показателей;
- понятные empty states;
- одинаковые UX-паттерны во всех разделах;
- mobile-first поведение для критических операций.

Главный экран — **рабочий, а не рекламный**.

Пользователь должен за несколько секунд понимать:

**где я → что происходит → что требует внимания → что я могу сделать дальше.**

## 15. Product principles

### 1. Data over decoration

Интерфейс не должен скрывать отсутствие данных за красивыми карточками.

### 2. No fake certainty

Если данных нет — приложение показывает отсутствие данных, а не придумывает значение.

### 3. Calculation before interpretation

Сначала расчёт, затем AI-интерпретация.

### 4. One source of truth

Frontend, backend, контракты и документация синхронизируются через `main`.

### 5. Secure by boundary

Browser → API Gateway → Backend → Cloud services.

Секреты и внутренние сервисы остаются за API Gateway.

### 6. Production first

Любое изменение считается завершённым только после проверки typecheck → lint → tests → build и, где возможно, production smoke.
