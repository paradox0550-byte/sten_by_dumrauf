# STEN — система управленческого контроля ресторанного бизнеса

STEN (Smart Tracking & Economic Navigator) — рабочий интерфейс для владельца и руководителя ресторанного бизнеса. Его задача — быстро показывать финансовые отклонения, проблемные зоны и следующие управленческие действия.

**Принцип продукта:** «STEN — это не закон, STEN — реалии ресторана».

> Этот README описывает структуру репозитория и подтверждённые команды проекта. Наличие кода, спецификации или workflow само по себе не означает, что соответствующая функция проверена в production.

## Основные принципы

- **Данные важнее оформления.** Не выдавать демонстрационные, случайные или фиктивные значения за реальные.
- **Нет данных ≠ ноль.** Отсутствующее значение показывается как «—» / «Нет данных», а не превращается в ноль.
- **Сначала расчёт, затем интерпретация.** Финансовые показатели должны опираться на расчётный источник; AI объясняет результат, но не подменяет его.
- **Один рабочий контур.** Не смешивать данные разных организаций, ресторанов и подразделений.
- **Безопасная граница.** Секреты и доступ к облачной инфраструктуре не должны попадать в браузер или frontend bundle.
- **Одна задача — один PR.** Изменения должны быть небольшими, проверяемыми и понятными.
- **Без самовольного релиза.** Merge и production deploy выполняются только после отдельного согласования.

## Локальный запуск

Требуется Node.js `20.19+` и npm.

```bash
npm ci
npm run dev
```

Vite покажет локальный адрес приложения в терминале.

## Проверки перед PR

Запускайте из корня репозитория:

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

Дополнительный строгий build:

```bash
npm run build:strict
```

Проверки должны завершиться успешно. Если команда не запускалась или завершилась ошибкой, это нужно явно указать в описании PR. Успешный CI не заменяет проверку интерфейса в браузере.

## Финансовые и продуктовые правила

- Не менять финансовые формулы без отдельной задачи и проверки контрактов.
- Не вычислять повторно на клиенте показатели, которые приходят с сервера как рассчитанные.
- Не подменять ошибки API успешными пустыми данными.
- Не скрывать частичную загрузку данных: явно показывать статус и источник.
- Не переключать ресторан или период без явного действия пользователя.
- Не добавлять новые интеграции, фоновые действия или хранение пользовательских данных без проверки существующих контрактов.

## Документация: с чего начать

- `AGENTS.md` — правила разработки, проверки, безопасности и PR.

- `docs/BACKEND_ENV_CONTRACT.md` — переменные окружения backend.

## Git-процесс

1. `main` — основная ветка, с которой сверяется актуальное состояние проекта.
2. Для работы создаётся отдельная ветка от актуального `main`.
3. Один PR решает одну задачу и перечисляет изменённые файлы, проверки и оставшиеся ограничения.
4. До merge проверяются актуальность ветки, CI, diff и возможное влияние на frontend/backend/API.
5. Не удалять ветки, документы или workflow только по названию. Сначала проверить открытые PR, уникальные коммиты, ссылки и использование в CI/deploy.
6. Не менять backend, API Gateway, секреты, правила защиты веток или production deployment в рамках обычной frontend-задачи.

## Статус и границы достоверности

Репозиторий содержит frontend, backend-код, тесты, спецификации и конфигурацию CI/CD. Их наличие не подтверждает автоматически:
- успешный production deploy текущего `main`;
- доступность всех облачных сервисов;
- соответствие каждой спецификации текущему backend;
- прохождение ручного визуального QA;
- готовность всех интеграций и пользовательских сценариев.

Перед объявлением проекта готовым к закрытию нужно отдельно проверить: открытые PR, состояние CI на актуальном `main`, критические сценарии приложения, актуальность документации и реальное состояние production. До этого README не называет проект полностью проверенным или завершённым.

**Где я? Что происходит? Где теряем деньги? Что нужно сделать дальше?**
