# Инвентаризация документации, скриптов и конфигурации STEN

**Дата проверки:** 2026-10-29  
**База аудита:** `main` на момент проверки; удаление устаревших документов рассматривается отдельно в PR #218.  
**Область:** только инвентаризация. Этот документ не подтверждает production smoke и не заменяет сверку runtime с облачной конфигурацией.

## Правило принятия решений

- **Сохранить** — контракт, release/security gate, эксплуатационная инструкция или используемый CI/deploy-скрипт.
- **Сверить и обновить** — документ может быть полезен, но содержит конкретные исторические версии, старый auth flow или формулировки «уже реализовано» без runtime-подтверждения.
- **Кандидат на объединение/архив** — содержание частично повторяется; не удалять до переноса уникальных требований и ссылок.
- **Не удалять по одному названию** — файл может быть ручным recovery/deploy-артефактом.

### Особое замечание по версиям Node.js

CI использует Node 22; deploy workflow на момент проверки настраивает Node 20. Это расхождение стоит устранить отдельным небольшим PR после проверки совместимости Vite/пакетов и целевого runtime. В рамках инвентаризации версии не менялись.

### Особое замечание по контрастному браузеру

CI ставит Playwright через `npm install --no-save --no-package-lock playwright@1.56.1` и устанавливает Chromium. Это runtime-зависимость CI, но она не добавляется в lockfile. Не менять до проверки воспроизводимости установки и причины отдельной установки.

## 6. Сверка с исходниками: подтверждённые расхождения (2026-10-29)

Эти пункты проверены по содержимому `main`, а не только по названиям документов.

### Auth — документы противоречат друг другу и коду

- `src/pages/Unlock.tsx` реально содержит оба способа входа: четырёхзначный код через `POST /auth/unlock` и email/пароль через `login(email, password)`. Экран показывает «Введите код или войдите по email».
- `backend/index.js` в текущем дереве содержит обработчик `POST /auth/unlock` и `GET /auth/me`; версия файла указана как 5.4.0.
- `docs/STEN_PRODUCTION.md` описывает персональный код как текущий flow и говорит, что email/password UI удалён.
- `docs/DEPLOYMENT_CURRENT.md` говорит, что PIN login припаркован, запрещает восстанавливать `/auth/unlock`, а активный flow «перерабатывается» под email/password.
- `docs/SECURITY_AUDIT_2026-10.md` содержит finding об отсутствии `POST /auth/unlock` на audited main, но текущий `backend/index.js` его содержит. Это историческое утверждение аудита не соответствует проверенному текущему файлу.
- `docs/smoke-backend.md` ожидает `healthz version: 5.0.2`, а `backend/index.js` помечен 5.4.0. Этот smoke ожидаемый version нельзя считать актуальным без проверки фактически развёрнутой Cloud Function.

**Действие:** не менять auth код в рамках документационного аудита. Исправить документацию после отдельного решения, какой способ входа является каноническим для production, и сверки с реальным deployed runtime. Не объявлять один способ «активным» только по документации.

### API Gateway YAML — это не три равнозначных копии

- `api-spec.yaml` — OpenAPI 3.0.3, версия в шапке 4.3.0, содержит повреждённую кодировку русских описаний (mojibake) и утверждает соответствие `backend/index.js v4.3.0`.
- `api-gateway-spec.yaml` содержит тот же старый OpenAPI внутри поля `openapi_spec`, плюс метаданные Gateway. По заголовкам и описаниям это производная/упакованная копия `api-spec.yaml`, а не актуальный автоматически синхронизируемый контракт.
- `api-gateway.yaml` — отдельная короткая recovery-конфигурация с интеграциями Cloud Functions, включая Google Sheets; это не просто копия двух предыдущих файлов.

**Действие:** не удалять ни один файл до проверки того, какой YAML фактически использовался при последнем обновлении Gateway. Затем назначить один источник генерации и явно обозначить остальные как generated/recovery либо архивировать после проверки отличий. Кодировку и версию OpenAPI исправлять отдельным PR, не в рамках удаления документации.

### Пользовательские руководства — дублирование подтверждено, но различается содержание

- `STEN_USER_GUIDE.md` фокусируется на диалоге STEN, входе, загрузке документов и вопросах руководителя.
- `USER_GUIDE.md` подробнее объясняет Dashboard, Scope, P&L и рабочий цикл.
- В обоих руководствах встречаются описания возможностей, которые нужно подтверждать по интерфейсу/backend, поэтому механическое удаление одного приведёт к потере полезных инструкций.

**Действие:** объединить уникальные разделы в одно руководство после проверки экранов и auth. До этого сохранить оба, но назначить один canonical guide и дать из второго ссылку на него.

### Production-документы — пересечение подтверждено

`STEN_PRODUCTION.md` и `DEPLOYMENT_CURRENT.md` повторяют API host, YandexGPT, хранение секретов, поведение /ask и запрет превращать отсутствующие данные в ноль. При этом auth-утверждения расходятся (см. выше), а только `DEPLOYMENT_CURRENT.md` перечисляет конкретный Cloud Function/runtime/database.

**Действие:** `DEPLOYMENT_CURRENT.md` оставить эксплуатационным источником production endpoints/runtime после сверки с облаком; `STEN_PRODUCTION.md` оставить коротким production behavior/security contract со ссылкой на deployment guide. Не сливать документы, пока auth и фактический deploy workflow не согласованы.

### Node.js и CI

- `.github/workflows/ci.yml` использует Node 22.
- `.github/workflows/deploy-frontend.yml` использует Node 20.
- `package.json` требует Node `>=20.19.0`.

Это подтверждённое расхождение конфигураций, но оно не доказывает само по себе, что deploy сломан. Нужна проверка совместимости текущего Vite/пакетов с Node 20 и 22, затем отдельное изменение workflow с CI. В этом аудите версии не менялись.

### Миграционные скрипты

- `migrate-db.sh` делает потоковый `pg_dump | psql` и заявляет, что не удаляет объекты назначения; он меняет содержимое целевой БД, поэтому запускать его в рамках чистки нельзя.
- `migrate-storage.sh` копирует объекты из Yandex Object Storage в Cloud.ru через `rclone copy` без удаления целевых-only объектов. Это миграционный инструмент, не очевидный кандидат на удаление.

Оба скрипта оставить до подтверждения, что миграция больше не требуется. В рамках аудита они не запускались.
