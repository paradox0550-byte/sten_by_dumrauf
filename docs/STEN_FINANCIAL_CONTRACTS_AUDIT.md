# STEN — аудит финансовых расчётов и отображения данных

**Статус:** аудит исходного кода `main`; не является разрешением менять бизнес-формулы.  
**Область:** только frontend. Backend/API/БД не изменяются.

## Краткий вывод

В коде уже есть полезные общие модули, но финансовые экраны используют несколько параллельных способов вычисления. До рефакторинга необходимо зафиксировать фактический контракт знаков API и покрыть его тестами: механически заменить все формулы опасно, потому что это может изменить EBITDA, прибыль и цвет отклонений.

## Подтверждённые точки расхождения

### 1. Две разные модели расчёта EBITDA

- `src/lib/financialCalculations.ts` описывает модель STEN, в которой расходы уже отрицательные, а EBITDA — подписанная сумма выручки и расходов.
- `src/lib/financialAnalytics.ts` содержит `calculateSignedEbitda` с тем же контрактом: расходы отрицательные, их нельзя вычитать повторно.
- `src/pages/Budget.tsx` использует `calculateEBITDA(revenue, [cogs, payroll, opex])`, что согласуется с подписанной моделью.
- `src/lib/financeCalculator.ts` использует `safeSub(revenue, cogs, payroll, opex)`, то есть вычитает расходы из выручки и ожидает расходы положительными.
- `src/pages/Finances.tsx` передаёт значения статей P&L напрямую в `calculateFinance`. Передача подписанных отрицательных расходов в этот калькулятор приведёт к противоположному результату.

**Решение:** не менять расчёт до проверки реальных ответов `/api/pnl` и контрактов `src/lib/contracts/pnl`. Затем выбрать один канонический формат входа (предпочтительно явно подписанные строки P&L) и адаптировать остальные экраны на границе, а не менять знак в разных компонентах по-разному.

### 2. Несколько реализаций форматирования денег

- `src/lib/format.ts` — общий форматтер с ₽ / тыс. ₽ / млн ₽ и безопасным отображением отсутствующих значений.
- `src/lib/pnl.ts` содержит отдельный `formatMoney`, который всегда показывает рубли.
- `src/pages/PnL.tsx` импортирует форматтер из `lib/pnl.ts`, тогда как другие страницы используют `lib/format.ts` или собственный `Intl.NumberFormat`.

**Решение:** оставить парсинг ввода в `lib/pnl.ts`, а отображение перевести на общий форматтер только после проверки тестов и всех call sites. Масштаб — только для отображения; исходные значения API остаются в рублях.

### 3. Отсутствующие данные представлены неодинаково

- Общий `formatMoney` возвращает `—` для null/undefined/нечисловых значений.
- P&L и бюджет имеют локальные функции `moneyOrEmpty`, возвращающие «Нет данных».
- Analytics и Finances используют собственные функции отображения и/или общий форматтер.
- OperationalControlPage использует `—` для null.

**Решение:** выбрать общий визуальный контракт для каждого состояния: `—` для единичного отсутствующего значения, «Нет данных» для объясняющего пустого состояния, отдельные сообщения для ошибки доступа и недоступности источника. Не заменять отсутствующие значения нулём.

### 4. Классификация и агрегация статей

- `src/lib/financialRows.ts` уже содержит канонические ключи статей, агрегацию и список производных строк, которые нельзя сохранять как первичные данные.
- `src/pages/Analytics.tsx` и `src/pages/Finances.tsx` имеют собственные текстовые классификаторы статей.
- `src/pages/Budget.tsx` использует `canonicalArticleKey`, но отдельно формирует набор строк бюджета.

**Решение:** постепенно использовать единый классификатор с явным состоянием unknown. Не классифицировать неизвестную статью как расход или доход по догадке.

### 5. Рабочий контекст

Финансовые экраны используют `useScope` и `scopeQuery`, однако в разных компонентах могут быть собственные способы загрузки, ошибок и повторного чтения. Нужно проверить, что при изменении scope данные предыдущего ресторана не остаются видимыми во время новой загрузки или после отказа доступа.

**Решение:** проверять каждый запрос и состояние данных на смене `period/projectId/branchId/restaurantId/departmentId`; не считать localStorage подтверждением доступа.

## План безопасной унификации

1. Зафиксировать реальные примеры ответов API и контракт знаков без секретов и персональных данных.
2. Добавить unit-тесты на подписанные расходы, нулевую выручку, null, отрицательные значения и отклонения.
3. Определить канонические функции для финансовых вычислений и отображения.
4. Перевести по одному экрану за раз; сверять результат с исходным поведением и реальными ответами API.
5. Проверить отсутствие устаревших данных при переключении рабочего контура.
6. После каждого этапа выполнить typecheck, lint, tests и build.

## Ограничения

- Никаких изменений backend, API-контрактов, БД или облачных функций.
- Не менять финансовые формулы без подтверждения фактического формата API.
- Не подменять отсутствующие данные нулями.
- Не объединять навигацию, финансовую логику и визуальный редизайн в один PR.
- Production deploy остаётся ручным.
