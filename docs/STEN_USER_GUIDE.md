# СТЕН — инструкция владельца

## 1. Что это

СТЕН — ваш личный рабочий кабинет для управления ресторанным бизнесом. Главный экран — диалог. Вы не обязаны помнить названия разделов: можно просто написать, что нужно сделать.

Примеры:
- «Проанализируй P&L за август».
- «Найди в документах правило по списаниям».
- «Сравни план и факт ФОТ».
- «Какие показатели требуют внимания?».
- «Собери краткий план действий управляющего на завтра».
- «Разбери этот Excel и покажи отклонения».

Главный принцип: система работает с доступными реальными данными. Если данных нет, STEN должен сказать «Нет данных» и указать, что нужно предоставить.

## 2. Первый вход

1. Откройте сайт.
2. Введите персональный код.
3. После успешной онлайн-разблокировки устройство получает рабочую сессию.
4. На другом устройстве используется тот же персональный код.
5. Email, логин и пароль учётной записи для пользовательского интерфейса не нужны.

Без сети локальная оболочка и настройки могут отображаться, но пользовательская аутентификация не обходится локально. Облачные документы, синхронизация, расчёты через API и AI требуют соединения.

## 3. Главный экран STEN

Главный экран специально сделан главным рабочим местом. Введите вопрос и нажмите Enter. Для новой строки используйте Shift+Enter.

Можно прикреплять PDF, DOCX, XLSX, XLSM, CSV, TXT, MD, JSON, XML и HTML. После загрузки документ появляется в списке и показывает состояние обработки.

## 4. Как правильно ставить задачи

Лучше описывать задачу обычным языком, но указывать период и объект.

Хорошо: «Проанализируй P&L ресторана за август 2026. Покажи PLAN, FACT, Δ и три главных отклонения».

Ещё лучше: «Сравни август с июлем. Найди рост себестоимости и проверь, есть ли подтверждение причины в загруженных документах».

Если причина не подтверждена источником, она не должна подаваться как факт.

## 5. Документы

Документ можно загрузить один раз и затем использовать в следующих вопросах, если backend хранит его в рабочем контуре. STEN использует название документа, извлечённый текст, найденные фрагменты и контекст задачи.

Практический сценарий: Excel P&L → загрузка → обработка → вопрос STEN → поиск данных → расчёт → объяснение.

## 6. P&L

P&L предназначен для контроля выручки, себестоимости, Food Cost, ФОТ, OPEX, финансовых расходов, налогов, EBITDA и чистой прибыли. Главный экран P&L показывает PLAN / FACT / Δ / Δ %. Числа должны приходить из расчётного контура.

## 7. Импорт P&L

Откройте «Импорт P&L», выберите Excel/CSV, проверьте распознанные статьи и периоды, при необходимости измените группу, сохраните импорт и затем проверьте P&L. Исходные названия статей сохраняются. Каноническая группа нужна для аналитики, а не для уничтожения вашей структуры.

## 8. Бюджет

Бюджет — плановый контур. Используйте его для плановой выручки, ФОТ, себестоимости, OPEX и сравнения план/факт. Не смешивайте план с фактом. Если фактического значения нет, показывается отсутствие данных, а не ноль.

## 9. Финансы

Раздел «Финансы» предназначен для фактической картины денежных показателей: выручка, наличные, безнал, расходы из фактических отчётов и фактический ФОТ. Для детального разбора переходите в P&L.

## 10. Экономика

Раздел связывает табель, фактические часы, ФОТ, выручку, план и отклонение. Цель — понять, за счёт чего изменился ФОТ. Пример: «Проверь, почему ФОТ выше плана, и отдели подтверждённые причины от гипотез».

## 11. Настройки

Можно выбрать светлую, системную или тёмную тему. Любой вспомогательный рабочий блок можно временно скрыть. Скрытие не удаляет данные. «Вернуть все» восстанавливает стандартный набор.

Очистка локальных данных удаляет только локальный кэш и черновики. Облачные документы этим действием не удаляются.

## 12. Память

История диалога нужна для продолжения работы. Документы хранятся в рабочем облачном контуре. P&L, отчёты и смены обрабатываются как структурированные данные. Результаты анализа могут сохраняться, если это предусмотрено backend.

Модель сама по себе не является базой данных. Память обеспечивается приложением и его хранилищами.

## 13. Работа без интернета

При отсутствии связи локальная оболочка и настройки могут отображаться, но рабочая сессия требует серверной аутентификации. Новые облачные документы, синхронизация и AI-запросы возобновляются после появления сети. Один персональный код может использоваться на разных устройствах; облачная версия данных общая.

## 14. Источники

Если ответ содержит источники, STEN использовал конкретные документы или структурированные данные. Для финансового ответа желательно видеть период, источник, формулу, результат, отклонение и вывод. Отсутствие источника — повод проверить данные.

## 15. Работа с цифрами

Правильный порядок: Факт → расчёт → отклонение → причина → действие.

Например: Food Cost = 37,2%; ориентир 25–35%; отклонение +2,2 п.п. Причина не устанавливается, если в данных нет подтверждения. Следующий шаг — проверить закупочные цены, списания, рецептуры и структуру продаж.

## 16. Чего не делать

Не просите STEN угадывать цифры. Нельзя использовать придуманные KPI, случайные значения, старые demo-экраны или данные из примера вместо фактических данных. Если данных нет, сначала загрузите источник.

## 17. Ежедневный сценарий управляющего

Утро: открыть STEN → спросить «Что сегодня требует внимания?» → проверить выручку и ФОТ → при необходимости открыть документы → сформировать план действий.

Днём: добавить отчёты → загрузить важные документы → проверить отклонения → задать уточняющие вопросы.

В конце периода: загрузить P&L → проверить PLAN/FACT → ФОТ → Food Cost → OPEX → EBITDA → причины отклонений → список действий.

## 18. Архитектура

Frontend: React + TypeScript + Vite. Хостинг: Yandex Object Storage. API: Yandex API Gateway. Backend: отдельная Yandex Cloud Function. База: PostgreSQL в Yandex Cloud. AI: внутренний backend-контур. Браузер напрямую к AI не обращается.

## 19. Правило обновлений

main является единственной истиной проекта. Перед изменением проверяются зависимости, импорты, маршруты, API-контракт, реальные источники данных, typecheck и build. При падении CI сначала получают реальную ошибку, затем исправляют причину.

## 20. Production-контур

Frontend публикуется в Object Storage. Для SPA index.html — главная страница, 404.html — shell для клиентских маршрутов. Deployment не должен удалять весь бакет, потому что в нём могут находиться пользовательские документы.

## 21. Контроль перед выпуском

Обязательны: npm run typecheck; npm run build; проверка dist/index.html; assets; manifest; service worker; MIME JS/CSS; HTML для / и /unlock; правильный API Gateway; отсутствие legacy login/password UI; отсутствие mock/demo KPI; отсутствие прямого AI из браузера; отсутствие секретов в frontend bundle.

## 22. Главный принцип

СТЕН нужен не для красивого разговора с моделью. Его задача: реальные данные → документы → расчёт → проверка → объяснение → управленческое решение. Если система не знает — она говорит, что не знает. Если число можно посчитать кодом — число считает код. Если причина не доказана — она помечается как требующая проверки.
