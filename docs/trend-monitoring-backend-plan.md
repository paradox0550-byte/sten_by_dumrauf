# STEN Trend Intelligence — отдельный план backend

## Решение по поиску

Google выбран основной поисковой системой пользовательского исследования в STEN. Это не означает, что браузерный Google Search уже предоставляет STEN API для автоматического сбора результатов.

Проверка официальной документации на 28.10.2026:
- Google Custom Search JSON API закрыт для новых клиентов; существующим клиентам предписан переход на альтернативу до 1 января 2027 года. Не закладывать этот API как основу нового продукта: https://developers.google.com/custom-search/v1/overview
- Официальный Google Trends API доступен через ограниченную alpha-программу, поэтому нельзя считать доступ гарантированным: https://developers.google.com/search/apis/trends
- Vertex AI Search — вариант для поиска по заданному набору доменов, но это не эквивалент полнотекстового поиска всего открытого веба.

## Рекомендуемое решение

Использовать Google как интерфейсный default для ручного поиска, а для автоматического сбора построить серверный адаптер провайдера. Перед production-реализацией проверить доступность и условия выбранного поставщика SERP API, стоимость, лимиты, географию и право сохранять/обрабатывать результаты. Не делать парсинг HTML Google основным production-механизмом: он хрупок, может нарушать условия сервиса и блокироваться.

Рекомендуемые этапы:
1. **Provider adapter:** единый интерфейс поиска; конфигурация провайдера на сервере; секреты только в secret manager/environment, никогда во frontend или репозитории.
2. **Источники:** Google SERP через легально доступный API-поставщик + белый список отраслевых сайтов/первичных источников. Отдельно подключать Google Trends только при получении официального доступа либо после оценки допустимого альтернативного провайдера.
3. **Сбор по расписанию:** weekly job с идемпотентностью, ограничением запросов, повторными попытками с backoff и явным состоянием ошибки. Ручной запуск — тот же pipeline без ожидания расписания.
4. **Нормализованная запись доказательства:** provider, query, canonical URL, title, snippet/excerpt, source domain, published_at (nullable), collected_at, market/geography, language, topic, fetch status, content hash и ссылка на исходный материал.
5. **Хранилище сигналов:** signal ID, формулировка, evidence links, независимость источников, противоречащие данные, временной ряд, confidence с объяснением, применимость к ресторану отдельно от коммерческого эффекта, статус проверки и результат эксперимента.
6. **Качество:** дедупликация URL/контента; выявление перепечаток; stale-source checks; отдельная обработка неизвестной даты; ограничение частоты; audit trail; метрики стоимости и ошибок.
7. **API для frontend:** защищённые endpoints для ручного запуска, статуса задания, списка сигналов, деталей сигнала, источников и результата эксперимента. Каждый ответ содержит статус и доказательства; неуспешный сбор не превращается в пустой список «трендов».
8. **Изоляция контуров:** проверять доступ к организации/рабочему контуру на каждом endpoint; не смешивать данные разных ресторанов. Общерыночные источники могут быть глобальными, а оценка применимости и результаты тестов — scoped к организации.
9. **Проверки:** unit/integration tests для дедупликации, дат, источников, тайм-аутов/429/5xx, повторов, прав доступа, пустых данных, ошибок провайдера и расписания.

## Что требуется до backend-кода

- Выбрать и проверить конкретный Google SERP API-поставщик (доступ, цена и условия ещё не подтверждены).
- Решить, где выполнять scheduled job и хранить доказательства, исходя из уже существующей инфраструктуры STEN.
- Определить допустимый бюджет запросов в неделю.
- Согласовать минимальную политику хранения исходных текстов: предпочтительно хранить метаданные и короткие выдержки, а не копировать целые статьи.
- Проверить, можно ли получить официальный доступ к Google Trends API alpha; не блокировать первый этап из-за ожидания alpha.

## Граница изменений

Этот документ — спецификация backend-этапа, не реализация. Backend/API/БД/Cloud Functions/секреты/планировщик не менялись. Деплой не выполнялся. Сначала нужно проверить провайдера и текущие контракты STEN, затем оформить backend-изменения отдельным PR после явного подтверждения backend-объёма.

## Критерии готовности backend

- Автоматическое обновление реально запускается по расписанию и показывает last success/last failure.
- Каждое утверждение о тренде связано с проверяемыми источниками и датами.
- Рынок РФ и мировой рынок остаются различимыми.
- Confidence и коммерческий эффект не подменяют друг друга; оценка содержит объяснение.
- При сбое источника отображается ошибка/неполнота, а не выдуманный сигнал.
- Данные и действия организации изолированы по scope.
- Секреты не попадают в клиент, логи или Git.
