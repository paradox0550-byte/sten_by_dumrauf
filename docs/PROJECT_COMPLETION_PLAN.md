# STEN — план завершения продукта

Основание: аудит исходников `main`, проведённый 2026-10-20. Этот документ фиксирует порядок работ и границы изменений. Он не утверждает, что сценарии уже проверены в работающем браузере.

## Продуктовый принцип

STEN — управленческий слой для оптимизации реального ресторанного бизнеса. Он помогает достигать целей, предупреждать потери и проверять эффект действий. STEN не заменяет POS/ERP и не навязывает всем ресторанам одинаковые правила.

- Конфигурация должна учитывать особенности конкретного ресторана, подразделения и периода.
- Факт, план, начисление, выплата, прогноз и гипотеза должны быть различимы.
- Отсутствующее значение не равно нулю.
- Каждый финансовый результат должен иметь источник и проверяемую формулу.
- Backend, OpenAPI, БД и Cloud Functions не изменяются без отдельного подтверждения конкретной необходимости.

## Аудит текущего состояния

### «Мой день» / оперативный контроль

Текущая страница `src/pages/OperationalControlPage.tsx` работает с дневным отчётом `/reports` и числовыми полями выручки, чеков, гостей, наличных, карты и скидок. Она не является универсальным реестром доходов и расходов.

В `src/pages/PnL.tsx` уже есть отдельный поток `POST /api/pnl/transactions` с выбором статьи, типа income/expense, даты, суммы, комментарием, экраном подтверждения и обновлением P&L. Документ `docs/PNL_MANUAL_ENTRY_CONTRACT.md` указывает, что операции прибавляются к факту статьи, поэтому тот же факт нельзя одновременно внести в ручной факт/импорт и как операцию.

Решение: сначала проверить существующий контракт и реальный путь сохранения/повторного чтения; затем переиспользовать существующий поток из «Моего дня», не создавая параллельный механизм. Регулярные шаблоны и автоматическое создание будущих операций нельзя имитировать локальным состоянием и нельзя считать реализованными, пока не подтверждено подходящее серверное хранение.

### ФОТ

Текущая `src/pages/Team.tsx` читает `/fot-analytics` и показывает агрегацию по подразделениям, часам и сумме. В `backend/core/tools.js` функция `getFot` выбирает только `period, department, hours, amount` из `payroll_records`; при любом выбранном scope возвращает `FOT_SCOPE_NOT_IMPLEMENTED`.

Следствие: текущий ответ API не подтверждает доступность детализации по сотруднику, должности, ставке, видам часов, начислениям, премиям и фактическим выплатам. Не отображать эти показатели как будто они существуют. Frontend может улучшить структуру и корректную обработку доступных данных, но полноценная достоверная детализация может потребовать отдельного согласованного расширения backend/API.

## План реализации

### Этап 0 — контрактная диагностика (до крупных изменений)
- Сопоставить frontend-контракты с фактическими обработчиками API для дневных отчётов, финансовых операций, P&L и ФОТ.
- Проверить организационный scope и фильтрацию периода.
- Определить, какие поля реально сохраняются и возвращаются.
- Зафиксировать пробелы отдельно; на этом этапе backend не менять.

Критерий выхода: матрица «поле → источник → API → сохранение → чтение обратно → бюджет/P&L».

### Этап 1 — «Мой день» как ежедневная точка управления
- Перестроить интерфейс вокруг дня/смены, входящих данных, регулярных обязательств, доходов и расходов, состояния проверки и контрольных сигналов.
- Для разовых подтверждённых операций использовать существующий `/api/pnl/transactions` и существующие статьи текущего scope.
- Не смешивать денежный поток с P&L без явного правила; явно показывать, куда влияет запись.
- Не показывать «сохранено», пока API не подтвердил запись и повторное чтение.
- Регулярные платежи должны отличаться от фактически совершённых операций. Автогенерацию повторов не добавлять без подтверждённого хранилища/контракта.
- Поддержать ресторанные варианты классификации через доступные статьи P&L; не зашивать универсальные трактовки доставки, представительских и иных специфических доходов/расходов.

Критерии приёмки: операция создаётся один раз; дата и scope верны; статья присутствует в P&L выбранного контура; после сохранения есть readback; не появляется двойной учёт при импорте/ручном факте; пустые данные не становятся нулями.

### Этап 2 — ФОТ
- Сформировать интерфейс управления ФОТ с блоками: должности/подразделения, ставки и модель оплаты, плановые/фактические часы, начисления, премии, доплаты, выплаты, производительность.
- Каждую метрику показывать только при наличии соответствующего источника.
- Разделять количество премий, сумму премий, начисленные и выплаченные суммы.
- Рассчитывать стоимость часа и выручку на час только при достаточных исходных данных.
- Отдельно проверить отсутствие поддержки scope в текущем API.
- Если детализации нет, подготовить конкретный список минимально необходимых контрактных изменений для отдельного согласования; в рамках frontend-only этапа не подменять это фиктивными полями.

Критерии приёмки: видны источник, период и scope; агрегаты сходятся с исходными данными; нет преобразования неизвестных значений в ноль; ставка и премия не выводятся из суммы без основания.

### Этап 3 — связность финансового контура
- Проверить связь ежедневных операций с P&L и бюджетом.
- Сохранить правило отклонения P&L = факт − план.
- Для расходов положительное превышение трактовать как неблагоприятное, отрицательное — как благоприятное, если конкретная статья не имеет иной явно заданной семантики.
- Проверить выручку по типам поступлений, скидки, возвраты и возможные представительские операции.
- Проверить дублирование факта между операциями, ручным вводом и Excel-импортом.

### Этап 4 — предупреждения и контроль исполнения
- Ранжировать отклонения по финансовому эффекту, срочности и достоверности данных.
- Показывать причину только если она подтверждена; иначе — «гипотеза, требуется проверка».
- Связывать сигнал с действием, ответственным, сроком и последующим измерением результата.
- Настраиваемые нормы/допуски учитывать на уровне конкретного ресторана, не объявляя общие ориентиры законом.

### Этап 5 — STEN AI
- Проверить ответы на реальных сценариях с пропущенными, противоречивыми и устаревшими данными.
- Для каждого финансового вывода показывать использованные показатели и формулу.
- Отделять факты от гипотез и прогнозов.
- Запрещать уверенный вывод при недостатке данных; не давать ИИ напрямую менять финансовые записи без явного подтверждения пользователя.

### Этап 6 — приёмка и запуск
- CI: typecheck, lint, tests, build.
- Проверки мобильного и desktop-интерфейса, светлой и тёмной тем.
- Проверки scope, ошибок API, повторной отправки, пустых ответов и восстановления после ошибки.
- Сквозная сверка данных с исходным отчётом ресторана.
- Документировать открытые ограничения до выхода на рынок.

## Границы безопасности

- Не менять backend/API/OpenAPI/БД/Cloud Functions без отдельного согласования.
- Не создавать финансовую истину в localStorage.
- Не генерировать демо-значения для заполнения пробелов.
- Не считать HTTP-успех доказательством сохранения, если контракт требует повторного чтения.
- Не сливать изменения в `main` без проверки diff, CI и отдельного подтверждения пользователя.
