# STEN → Cloud.ru: план аудита и выполнения миграции для AI-агента

> **Назначение:** передать ИИ-агенту (Claude Code / Cloud / другой агент с доступом к репозиторию) единое проверяемое задание: изучить реальное состояние STEN, устранить подтверждённые проблемы подготовки миграции и проверить готовность Cloud.ru. Документ не является подтверждением, что миграция уже выполнена.

## Инструкция агенту

Открой репозиторий `paradox0550-byte/sten_by_dumrauf`, прочитай этот документ целиком, затем изучи код, конфигурацию, документацию, историю Git и результаты CI. Работай по этапам ниже, сохраняя фактические результаты и ссылки на файлы/коммиты.

**Не ограничивайся планом или советами:** если у тебя есть доступ на чтение и запись в GitHub/рабочую копию, выполни разрешённые изменения в отдельной ветке, прогони доступные проверки, подготовь PR и отчёт. Если у тебя нет доступа или инструментов для конкретного действия, прямо назови блокер и предоставь точные команды/шаги — не утверждай, что действие выполнено.

## Жёсткие ограничения

1. Не переключай production на Cloud.ru и не меняй production API URL фронтенда до завершения проверок и отдельного явного подтверждения владельца.
2. Не создавай платные Cloud.ru/Yandex Cloud ресурсы, не запускай миграцию данных и не меняй тарифы без отдельного согласования.
3. Не удаляй, не останавливай и не модифицируй существующие ресурсы Yandex Cloud. Они остаются резервным рабочим контуром.
4. GitHub Actions не должен развёртывать backend, API Gateway, Cloud Functions или MarkItDown. Разрешённый frontend deploy в Object Storage не расширять.
5. Не выводи секреты, токены, пароли, connection strings и значения чувствительных env-переменных в отчёты, логи, issue или PR. Проверяй только наличие/имена и безопасные метаданные.
6. Не меняй бизнес-логику STEN, AI-провайдера или backend/API без доказанной необходимости и отдельного согласования. AI-провайдер — YandexGPT, не Ollama.
7. Не подменяй отсутствующие данные предположениями. Отделяй подтверждённые факты, выводы и неизвестные. «Нет данных» не означает ноль.
8. Не выполняй force-push, destructive commands, миграцию БД/объектов или переключение DNS/API без явного разрешения.
9. Не объявляй миграцию готовой только потому, что конфигурационные файлы существуют или CI прошёл.
10. Перед изменением существующего файла проверь его текущее состояние и каскад зависимостей. Изменения должны быть минимальными и обратимыми.

# Этап 1. Аудит текущего состояния — без изменений

Сначала ничего не меняй.

1. Определи актуальные `main`, рабочие ветки, последние коммиты, открытые PR и состояние CI.
2. Прочитай README, инструкции разработки и деплоя, файлы миграции Cloud.ru, Dockerfile/контейнерные конфиги, API Gateway/OpenAPI, frontend env-конфигурацию, GitHub Actions и тесты.
3. Построй карту архитектуры: frontend → API Gateway → backend → БД / Object Storage → MarkItDown → YandexGPT. Отметь подтверждённые соединения и те, которые только предполагаются.
4. Найди все места, где задаются URL API, CORS, auth, таймауты, лимиты запросов, health checks, readiness/liveness, настройки БД и S3/Object Storage.
5. Проверь workflow на запрещённый deploy backend/API Gateway/Cloud Functions/MarkItDown. Проверь репозиторий на потенциально опубликованные секреты, не копируя значения секретов в вывод.
6. Проверь совместимость конфигурации Cloud.ru с актуальной документацией платформы, если доступ к документации есть. Чётко различай документированные возможности, настройки проекта и неизвестные параметры.
7. Проверь миграционные риски: совместимость БД и SQL, миграции схемы, роли/права, транзакции, расширения, timezone, кодировки, большие объёмы, резервная копия и восстановление, Object Storage/S3 API, CORS и лимиты.
8. Запусти безопасные локальные проверки и тесты, которые не меняют внешнюю инфраструктуру.

**Результат этапа 1:** добавь в отчёт таблицу «проверка / результат / доказательство / риск / следующий шаг», список P0/P1/P2, карту зависимостей и список неизвестных. Для каждой проблемы приведи путь к файлу и строки/ссылку на CI или официальный источник. Не делай изменений до завершения отчёта.

# Этап 2. Исправления в отдельной ветке — без деплоя и миграции

После аудита:

1. Создай рабочую ветку от актуального `main`; не работай непосредственно в `main`.
2. Исправь только подтверждённые проблемы подготовки миграции и документации. Не переписывай архитектуру и не добавляй неиспользуемые абстракции.
3. Приведи конфигурацию API Gateway к формату, который подтверждён актуальной документацией Cloud.ru. Не угадывай расширения или поля. Если подтвердить невозможно — зафиксируй блокер, не маскируй его.
4. Убедись, что backend routes, HTTP methods, query parameters, headers, request body, status codes и ошибки корректно проходят через gateway.
5. Проверь CORS для реального frontend origin, включая OPTIONS preflight, POST и Authorization. Не используй wildcard для credentials.
6. Проверь rate limiting, auth, health checks, startup/shutdown, таймауты, размеры body и поведение при недоступности БД/MarkItDown.
7. Проверь контейнеры на корректный запуск, non-root где возможно, минимальный набор пакетов, отсутствие секретов в слоях и логах.
8. Обнови только необходимые инструкции: переменные окружения по именам без значений, build/run, health checks, миграция/rollback, проверки после развёртывания и восстановление на Yandex Cloud.
9. Добавь/обнови тесты для исправлений. Не добавляй фиктивные тесты, которые просто подтверждают константы или не проверяют поведение.
10. Запусти доступные тесты, lint, typecheck, build и security checks. Если что-то не запускается, укажи точную причину.
11. Создай PR с кратким описанием, рисками, списком проверок и оставшимися блокерами.

**Запрещено на этапе 2:** deploy, создание ресурсов, импорт/экспорт реальных данных, изменение production URL, переключение трафика, удаление/остановка Yandex Cloud ресурсов.

# Этап 3. Проверка готовности Cloud.ru и решение GO / NO-GO

Проводи этот этап только на основании доступных подтверждений. Не создавай ресурсы и не запускай миграцию.

Составь таблицу с доказательствами по каждому пункту:

- Cloud.ru Container Apps: реальные URL и состояние `sten-backend` и `sten-markitdown` (если существуют и доступны для просмотра).
- Backend: health/readiness, логи без секретов, доступность необходимых зависимостей.
- API Gateway: корректные upstreams, маршруты, методы, заголовки, query/body, коды ошибок, auth, rate limits.
- CORS: preflight OPTIONS и реальные запросы из разрешённого origin.
- Database: совместимость, способ безопасного переноса, оценка объёма/простоя, backup, проверка целостности и план rollback. Никаких операций с данными без согласования.
- Object Storage: совместимость API, bucket policy, IAM, CORS, размер/тип объектов и план переноса/возврата.
- Secrets: безопасное хранение, доступы с минимальными правами, отсутствие секретов в репозитории/логах.
- Observability: логи, метрики, ошибки, оповещения и процедура диагностики.
- Frontend: конфигурация API и возможность отдельного тестового окружения без затрагивания production.
- Стоимость: только предварительная оценка с тарифными источниками и явно обозначенными предположениями; никаких платных ресурсов не создавать.
- Rollback: условия остановки, последовательность возврата к Yandex Cloud и проверка работоспособности fallback.

В финале выдай один статус:

- **NO-GO** — есть критические неизвестные, отсутствуют URL/доступы/проверки, или есть ошибки.
- **CONDITIONAL GO** — проверки кода пройдены, но нужны внешние действия владельца или подтверждения Cloud.ru.
- **GO FOR OWNER APPROVAL** — технические проверки подтверждены; это всё ещё не разрешение на production-переключение.

Даже при GO не переключай production, не мигрируй данные и не создавай платные ресурсы без отдельного явного разрешения владельца.

## Формат итогового отчёта

1. Краткий статус и что реально выполнено.
2. Коммиты, ветка и PR-ссылки.
3. Изменённые файлы и зачем.
4. Проверки: команда/CI → PASS/FAIL/SKIPPED → ссылка/доказательство.
5. Блокеры и неизвестные.
6. Риски и rollback.
7. Стоимость — только если есть проверяемые тарифные данные.
8. Статус GO / NO-GO с обоснованием.
9. Чёткий список действий, которые должен выполнить владелец.

**Главное:** исследуй фактический репозиторий и реальные результаты. Не выдавай предположения за проверку и не заявляй об изменениях, которые не были выполнены.
