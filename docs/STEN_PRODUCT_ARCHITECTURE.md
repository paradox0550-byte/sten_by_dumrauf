# STEN — целевая продуктовая и frontend-архитектура

**Статус:** архитектурный канон для поэтапного внедрения  
**Область:** продуктовая структура и frontend  
**Ограничение:** backend, API-контракты, база данных и облачные функции не изменять без отдельного разрешения.

## 1. Что такое STEN

STEN — управленческий контур ресторана: помогает руководителю понимать финансовый результат, замечать отклонения, контролировать операционные процессы и назначать действия. Это не POS, не касса и не замена учётной системе.

Главный пользовательский результат: за несколько секунд ответить на четыре вопроса:
1. Где я работаю — организация, ресторан/филиал, период?
2. Что происходит с бизнесом — план, факт, отклонения, качество данных?
3. Что требует внимания прямо сейчас?
4. Какое следующее действие можно выполнить и как проверить результат?

## 2. Каноническая навигация

Навигация описывает работу руководителя, а не внутреннее устройство кода. Не создавать новые экраны, если можно ясно разделить ответственность существующих.

### Главная
- **Обзор** (/dashboard) — управленческий cockpit: ключевые показатели, критические отклонения, полнота данных и следующие действия.
- **STEN AI** (/, /sten, /ai) — единое интеллектуальное рабочее пространство. Плавающий помощник не должен дублировать полноценный чат.

### Финансы
- **P&L** (/pnl) — единый отчёт о прибыли и убытках: план/факт, статьи, расчётные показатели, подтверждение и история статуса, если это поддержано серверным контрактом.
- **Бюджет** (/budget) — бюджетные правила и планирование по периодам/статьям. Не превращать экран в копию P&L.
- **Финансовые операции** (/finances) — реестр первичных доходов/расходов с датой, статьёй, суммой, типом поступления, источником и состоянием проверки. Не подменять им P&L.
- **Аналитика** (/analytics) — объяснение отклонений и динамики, сопоставление доступных данных. Не дублировать таблицу P&L.

### Операционное управление
- **Отчёт смены** (/ops; исторические /my-day, /quick-entry, /flash ведут сюда) — ввод/проверка сменных фактов: выручка, чеки, гости, наличные, безнал, скидки и другие поля, поддержанные контрактом.
- **План руководителя** (/plan; исторический /secretary ведёт сюда) — задачи, напоминания и контроль исполнения. Не является вторым AI-чатом.
- **Команда и ФОТ** (/staff; исторический /team ведёт сюда) — сотрудники, графики, ставки, часы, прогноз и стоимость труда в пределах реально доступных данных.
- **Документы** (/documents) — загрузка и поиск источников, предпросмотр извлечённого содержимого, переход к документу-основанию. Документ не считается подтверждённым фактом автоматически.

### Знания и контроль
- **Память STEN** (/memory) — поиск решений и контекста прошлых разговоров с явным разграничением памяти диалогов и источников-документов.
- **Настройки** (/settings) — профиль, организация и рабочий контур, вид/доступность блоков, персонализация AI и подключённые интеграции.
- **Правовая информация** (/legal) — доступна из настроек/подвала, не занимает место в ежедневной навигации.
- **Организации** (/admin/organizations) — только для роли с соответствующими правами.
- **Лаборатория AI** (/ai-quality) — служебный инструмент контроля качества; не основной пункт ежедневной навигации.

## 3. Единый рабочий контекст

Верхняя панель постоянно и однозначно показывает выбранный период и рабочий контур. Контур включает организацию и доступный уровень иерархии: проект → филиал → ресторан → отдел.

Правила:
- Переключение контекста распространяется на все финансовые и операционные экраны.
- Нельзя молча переносить пользователя на другой ресторан, если текущий контур не сохранён или недоступен.
- Сервер — источник истины; localStorage — только кэш/удобство, не источник полномочий.
- Ошибка сохранения контекста видима пользователю; AI и финансовые запросы не должны продолжать использовать заведомо устаревший выбор.
- «Все» означает только доступных потомков выбранного родительского уровня, а не всю организацию по умолчанию.
- При отсутствии обязательного контекста показывать ясное состояние и действие выбора, а не пустые цифры и не случайный ресторан.

## 4. Контракт достоверности данных

Каждый показатель и каждая строка должны по возможности иметь значение и единицу измерения, период и scope, источник/происхождение, подтверждённый статус, формулу и версию расчёта для производных метрик, а также действие для проверки/исправления, если оно реально поддержано.

Жёсткие правила:
- Отсутствующее значение — null, «—» или «Нет данных», никогда не фиктивный ноль.
- Никаких mock-значений, выдаваемых за реальные данные.
- Расчётные показатели рассчитывает детерминированный код/сервер, AI только интерпретирует.
- Один показатель не должен иметь несколько независимых формул на разных страницах.
- Единицы и масштабы ₽ / тыс. ₽ / млн ₽ применяются единообразно, API получает базовые рубли.
- Для расходных отклонений направление выгодности не такое, как для выручки; цвета следуют экономическому смыслу, а не знаку сами по себе.
- Действия «сохранить», «подтвердить» и «отправить» имеют разные значения и не имитируют серверное сохранение.

## 5. Связный рабочий цикл

1. **Источник:** отчёт смены, финансовая операция, импорт или документ.
2. **Проверка:** формат, период, статья, ресторан, дубликаты и полнота.
3. **Подтверждение:** пользователь видит, что будет записано; подтверждение фиксируется только при реальном подтверждении API.
4. **Отражение:** первичные записи попадают в соответствующие отчётные представления через существующие серверные контракты.
5. **Контроль:** P&L и обзор показывают план/факт, отклонения, источники и полноту данных.
6. **Действие:** руководитель создаёт задачу/решение в Плане руководителя, если endpoint существует.
7. **Проверка результата:** аналитика показывает новое состояние после обновления данных.

Ни один frontend-экран не должен имитировать недоступный этап локальным состоянием.

### Типы поступлений и расходов

Интерфейс должен различать категории поступлений, если они поддержаны бизнес-контрактом: кассовые, безналичные/доставка, представительские и прочие внекассовые поступления. Категория сама по себе не должна автоматически определять бухгалтерскую классификацию: способ бюджетирования задаётся для организации/ресторана и подтверждается правилами учёта. Нельзя менять серверную классификацию без отдельного согласования.

## 6. Роль STEN AI

STEN AI — единый интеллектуальный слой, а не отдельная система учёта.
- Получает текущие организацию, ресторан, период и разрешённый набор данных.
- Отделяет факты от интерпретаций и рекомендаций.
- Указывает источник факта и формулу, когда доступны.
- При недостатке данных прямо сообщает, чего не хватает.
- Не переключает scope самовольно.
- Не создаёт фиктивные записи и не объявляет действие выполненным без подтверждения сервера.
- Память разговоров и поиск по документам показывают происхождение найденной информации.
- Голос и встречи — последующие возможности после стабильности базового сценария.

## 7. Целевая структура frontend-кода

Цель — постепенный переход к структуре по бизнес-функциям, без массового перемещения файлов одним изменением:

    src/
      app/
        routing/          # маршруты, redirect-совместимость
        providers/        # auth, query, theme и глобальные провайдеры
        shell/            # AppShell, верхняя панель, навигация
      features/
        overview/
        ai/
        finance/
          pnl/
          budget/
          transactions/
          analytics/
        operations/
          shift-report/
          manager-plan/
          team-fot/
        knowledge/
          documents/
          memory/
        settings/
        workspace/
        legal/
      shared/
        ui/               # переиспользуемые визуальные компоненты
        api/              # единая транспортная обвязка и ошибки
        domain/           # scope, финансовые формулы, форматирование
        contracts/        # схемы запросов/ответов, совпадающие с API
        hooks/
        assets/
      styles/
        tokens.css        # единственный источник design tokens

Это целевая модель, а не требование немедленно переименовать все существующие директории. Текущие маршруты, API-контракты и публичные ссылки сохраняются через адаптеры/redirects. Не создавать дубликаты сущностей ради новой структуры папок.

## 8. Правила интерфейса

- STEN · Calm Intelligence: спокойный, точный, премиальный B2B-интерфейс; без неонового «хакерского» оформления.
- Один источник design tokens; не плодить параллельные палитры и случайные !important.
- Общие паттерны загрузки, ошибки, пустых состояний, подтверждения, таблиц и фильтров.
- Desktop — основной режим руководителя; tablet/mobile — полноценные сценарии быстрых проверок и ввода.
- В мобильной навигации только самые частые действия; остальные доступны в понятных группах.
- AI-лаборатория, администрирование и юридические страницы не конкурируют с ежедневными задачами.
- Никаких новых экранов или больших декоративных блоков без доказуемой пользы.

## 9. План миграции

Каждый этап — отдельная ветка/PR, одна задача, CI и ручная проверка. Не сливать всё одним огромным рефакторингом.

### Этап 0. Зафиксировать карту
- Инвентаризировать реальные страницы, маршруты, общие компоненты, дубли, источники данных и тесты.
- Проверить, какие функции реально работают в production, не полагаясь только на название пункта меню.
- Сформировать таблицу «экран → назначение → endpoint/источник → состояние данных → действие».
- Не менять backend и не делать production deploy.

### Этап 1. Информационная архитектура
- Привести sidebar и mobile navigation к каноническим группам выше.
- Убрать дублирующие пункты навигации, не удаляя маршруты и не ломая закладки.
- Скрыть служебные инструменты из ежедневной навигации, сохранив role guard.
- Сохранить глобальный выбор scope/периода.

### Этап 2. Общие контракты UI
- Унифицировать состояния loading/empty/missing/error/unavailable.
- Свести форматирование финансов и вычисление сигналов к общим доменным функциям.
- Добавить/обновить тесты на null, ноль, отрицательные отклонения, масштаб и scope.
- Не переписывать серверные формулы.

### Этап 3. Сквозной финансовый цикл
- Проверить запись операции и отчёта смены, серверный readback, P&L и подтверждение.
- Отделить план, факт, первичную операцию и производный показатель.
- Добавлять недостающие возможности только при наличии согласованного API-контракта.

### Этап 4. AI и знания
- Проверить scope-изоляцию, источники ответов, память и поиск документов.
- Устранить повторяющиеся точки входа, сохранив единое рабочее пространство AI.
- Не добавлять голос/встречи до надёжности базового сценария.

### Этап 5. Визуальная консолидация
- Единые токены, логотип, иконки, таблицы и состояния.
- Проверка светлой/тёмной темы и desktop/mobile.
- Не менять финансовую семантику в ходе визуального рефакторинга.

## 10. Definition of Done

Этап завершён, только если:
- npm ci, npm run typecheck, npm run lint, npm test, npm run build проходят;
- нет новых фиктивных данных и локального псевдосохранения;
- существующие маршруты и прямые ссылки работают;
- scope сохраняется и не пересекается между организациями;
- значения null остаются отсутствующими;
- финансовые формулы и экономические цвета не изменены случайно;
- интерфейс проверен на desktop и mobile;
- backend/API/DB не затронуты без отдельного разрешения;
- production deploy остаётся ручным и выполняется только владельцем.

## 11. Что не делать

- Не переносить все файлы и не переписывать приложение целиком в одном PR.
- Не менять backend ради удобства frontend без отдельного разрешения.
- Не добавлять новые дублирующие страницы «для красоты».
- Не создавать демонстрационные цифры, фиктивные операции и успешные статусы.
- Не удалять старые URL, которые могли быть сохранены пользователем.
- Не смешивать визуальный редизайн, навигацию и бизнес-логику в одном изменении.
- Не сливать в main и не запускать production deploy автоматически в рамках архитектурной работы.

---
**Главный критерий:** STEN должен быть не коллекцией разделов, а единым управленческим циклом: достоверный источник → проверка → финансовая картина → действие → контроль результата.
