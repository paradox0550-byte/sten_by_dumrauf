# Уроки STEN

## 1. TypeScript / copy-paste

### TS1005
Частая причина — повреждённый синтаксис после copy-paste:
- Unicode quotes;
- лишний/пропущенный символ;
- backslash;
- zero-width characters;
- неверно закрытый object/function call.

Правило:
сначала открыть фактическую строку и исправить структуру кода, а не делать слепую regex-замену.

### TS2322: unknown
JSON.parse и внешние данные имеют тип unknown.
Нужно явно сузить тип:
- type guard;
- проверка === true/false;
- безопасный fallback.

Не использовать any только для прохождения CI.

## 2. Yandex API Gateway / OpenAPI

- YAML anchors не поддерживаются так, как ожидается в некоторых конфигурациях Yandex API Gateway.
- Повторяющиеся options-блоки нужно разворачивать явно.
- В OpenAPI 3.0 exclusiveMinimum — boolean, а не numeric value.

Всегда проверять фактический контракт перед deploy.

## 3. CI ≠ browser QA

Зелёные:
- typecheck;
- lint;
- tests;
- build

не доказывают:
- правильную визуальную сетку;
- отсутствие clipping;
- мобильное поведение;
- keyboard focus;
- reduced-motion;
- реальные ощущения от density/composer.

Browser QA должен быть отмечен отдельно.

## 4. Diff discipline

Если задача предполагает удаление/замену кода, а Git показывает только +N/-0, это повод остановиться и проверить:
- base branch;
- merge-base;
- реальный diff;
- не попала ли старая версия файла в ветку.

Не считать размер diff доказательством качества.

## 5. Backend boundary

Frontend-задача не должна случайно менять:
- backend/**;
- Cloud Function;
- API Gateway;
- Lockbox;
- deployment workflow.

Backend меняется только в отдельной явно согласованной задаче.

## 6. Secrets

Секреты нельзя:
- писать в чат;
- коммитить;
- помещать в frontend;
- выводить в логи.

При подтверждённой утечке нужна ротация секрета, а не просто удаление строки из git.

## 7. Финансовые данные

- missing != zero;
- AI не является источником расчёта;
- сначала вычислить значение из данных;
- затем дать интерпретацию;
- источник и формула должны быть доступны для проверки.

## 8. STEN UX

- интерфейс должен помогать руководителю принимать решение;
- декоративность не должна конкурировать с финансовыми цифрами;
- Settings — пользовательские настройки, а не developer console;
- мобильный интерфейс не должен быть уменьшенной копией desktop;
- composer должен оставаться компактным.

## 9. Работа с PR

Перед merge:
1. актуальный main;
2. фактический diff;
3. CI;
4. ручная QA там, где нужна;
5. явное решение владельца проекта.

Не объявлять PR готовым к merge только потому, что CI зелёный.
