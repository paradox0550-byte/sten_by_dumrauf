# STEN — единая спецификация операционного дня, iiko, финансов и ФОТ

Статус: рабочая спецификация для PR #240. Это контракт проектирования; неподтверждённые поля и методы внешнего API не являются реализацией.

## Цель

Единая цепочка данных для руководителя: iiko → операционный день ресторана → предварительный/финальный отчёт → сверка финансовых моделей → табель и ФОТ → единый «Отчёт дня».

Не создавать параллельные механизмы, если в репозитории уже есть подходящий рабочий механизм. Перед изменением сверять существующий код, схему хранения, API и UI. Не переписывать работающие части ради рефакторинга.

## Неподвижные правила

- Источник истины для финансового закрытия — операционный день iiko, не календарная дата.
- Хранить отдельно `operational_date` и календарные timestamps; если даты отличаются, не нормализовывать одну в другую.
- Ключ дневной записи включает идентификатор ресторана iiko и идентификатор операционного дня iiko. Внешние ID смен/касс сохранять отдельно для детализации и сверки.
- Предварительный отчёт не закрывает операционный день и не попадает в P&L.
- Не объявлять отчёт финальным, пока достоверно не подтверждено закрытие операционного дня и всех относящихся к нему кассовых смен. Закрытие последней кассовой смены нельзя автоматически считать закрытием дня без подтверждения API-контрактом.
- Отсутствующие/неполные значения остаются null / «Нет данных», а не превращаются в ноль.
- Повторная доставка и повторный импорт должны быть идемпотентными; корректировки обновляют исходную запись с историей, а не создают второй дневной факт.
- Никаких main merge, deploy или backend production изменений без отдельного разрешения пользователя.

## Направление 1 — надёжность webhook Telegram

- Долговечное сохранение update до бизнес-обработки.
- Идемпотентный ключ Telegram `update_id`.
- Состояния pending / processing / processed, счётчик попыток, время lease, следующая попытка и последняя ошибка.
- Ошибка бизнес-обработки должна возвращать update в retryable state; активный update нельзя обрабатывать параллельно.
- Callback acknowledgement Telegram — отдельная best-effort операция: истёкший callback не должен отменять долговечную обработку update.
- Lease fencing: устаревшая попытка не может завершить или освободить lease более новой попытки.
- Интеграционные проверки с PostgreSQL и Telegram webhook обязательны до статуса готовности. Unit-тесты не заменяют проверку конкурентности в реальной БД.

## Направление 2 — аудит и единая финансовая модель P&L

- Единый серверный калькулятор — источник расчётных показателей; frontend не дублирует формулы.
- Проверить фактические входные категории и их соответствие модели: выручка, себестоимость, ФОТ, переработки (если отдельная статья), OPEX, прочие операционные, амортизация, проценты, налоги.
- Установить на основании существующего финансового контракта, входит ли overtime в payroll или хранится отдельно; не складывать повторно и не считать отсутствующую статью нулём.
- EBITDA допустима только при наличии всех обязательных компонентов согласованной модели. Если блок отсутствует, EBITDA и её маржа недоступны; показать перечень недостающих блоков.
- Чистая прибыль недоступна, пока отсутствуют обязательные статьи ниже EBITDA.
- Prime Cost = COGS + Labor по подтверждённому определению Labor; нормы и статусы не должны менять исходные суммы.
- Сохранить знак расходов и единое правило delta: факт − план; не допускать двойного вычитания отрицательных расходов.
- Excel импорт: распознавать формулы только по сохранённому Excel cached result; если результата нет — null и предупреждение. Неизвестные статьи сохранять отдельными строками без автоматического отнесения к «прочим». План и факт не подменять друг другом. Каждая строка содержит источник, лист, номер строки/ячейки и предупреждения.
- Проверить фактический frontend contract и все места использования calculatePnl/rollupAgg до включения новой модели.

## Направление 3 — интеграция iiko и дневной отчёт

### Предварительный отчёт
- Получать промежуточные показатели в 17:00 локального времени ресторана.
- По умолчанию показывать уведомление в STEN; Telegram-чат руководителей включается отдельно в настройках.
- Изменения цифр обновляют существующий предварительный отчёт и создают уведомление об изменении.
- Не закрывать операционный день и не передавать предварительные цифры в P&L.

### Финальный отчёт
Запрашиваем шесть показателей, но названия полей — только кандидаты до проверки схемы и реального ответа API:
- выручка (кандидат `totalSum`);
- количество чеков (кандидат `checksCount`);
- количество гостей (кандидат `guestsCount`);
- наличные — сумма платежей подтверждённых типов;
- карты/электронные платежи — сумма платежей подтверждённых типов;
- скидки (кандидат `discounts`).

Перед реализацией:
- подтвердить актуальный метод, версию API, авторизацию и схему ответа по официальной документации iikoCloud;
- получить пример реального ответа на доступе конкретной организации/версии;
- проверить часовой пояс ресторана, границы операционного дня и связь кассовых смен с операционным днём;
- выяснить, существует ли надёжный признак закрытия самого операционного дня. Поле `isClosed` и имена методов не закладывать до подтверждения.
Если API не позволяет достоверно подтвердить закрытие всего операционного дня и всех его смен, оставить отчёт в состоянии «ожидает подтверждения», не финализировать автоматически.

### Идемпотентность и сверка
- Один логический отчёт на пару (iiko restaurant ID, iiko operational day ID).
- Сохранять ID каждой кассовой смены и кассы, исходные payload/метаданные запроса и время получения.
- Повторный запрос обновляет запись того же операционного дня.
- Изменение после финального подтверждения фиксируется как корректировка с историей и требует повторной проверки.
- Повторная передача в P&L не создаёт дубль выручки/расходов.
- Пропущенный отчёт восстанавливается за исходный operational day ID, не за текущую календарную дату.

### P&L
- Кассовые смены — кандидат на источник выручки, пока не подтверждены схема и правила iiko.
- Себестоимость — отдельный показатель; источник и период сверяются отдельно.
- Отчёт iiko «Прибыль и убытки» используется для сверки до подтверждения точного соответствия периодов и статей.
- В P&L передаётся только подтверждённый финальный отчёт по согласованному процессу.

## Направление 4 — упрощённый импорт табеля и ФОТ

- Убрать график изменения расписания из целевого упрощённого сценария; оставить лимиты часов по подразделениям.
- Импортировать существующую онлайн-таблицу Excel без требования перестраивать её вручную, если формат можно надёжно распознать.
- Распознавать сотрудников, должности, подразделения, ставки и фактические часы.
- До сохранения показывать окно проверки с нераспознанными строками и неоднозначными совпадениями.
- Поддержать почасовую оплату, оплату за смену и оклад.
- Рассчитывать часы кухни, зала и других подразделений, стоимость рабочего времени и отклонения от лимитов.
- Полный ФОТ с офисом рассчитывать только при явном включении офисных сотрудников и правил их начисления.
- Сохранять историю периодов, импортов и корректировок; защищать повторный импорт от дублей.
- Сверить с текущими `src/domain/labor/imports`, `src/pages/FotScheduleImport.tsx`, FOT-моделью и хранилищем до изменения; не создавать второй парсер/источник истории.

## Единый «Отчёт дня»

Связывает только данные одного ресторана и одного операционного дня:
- состояние iiko: предварительный / ожидает закрытия / финальный / требует сверки;
- выручка, чеки, гости, наличные, электронные платежи, скидки;
- себестоимость и финансовая сверка;
- часы и стоимость смены по подразделениям;
- отклонения от лимитов;
- отсутствующие данные, ошибки интеграции и корректировки.

Отчёт не должен выдавать предварительные показатели за закрытые и не должен вычислять неизвестные показатели как ноль.
