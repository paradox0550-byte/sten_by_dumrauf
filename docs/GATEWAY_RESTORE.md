## Шаги в консоли Yandex Cloud

### 1. Открыть раздел API Gateway
Откройте консоль Yandex Cloud, каталог DU → API Gateway.

### 2. Создать новый шлюз
- Имя: `sten-gateway-v2`
- Описание: `STEN API Gateway (recovery after ru-central1-b incident)`
- Спецификация: `api-gateway.yaml` из репозитория.

### 3. Проверить права
Убедитесь, что сервисный аккаунт шлюза имеет роль `functions.functionInvoker` на обе функции. ID актуального сервисного аккаунта не был предоставлен и намеренно не выдуман.

### 4. Скопировать домен
После создания скопируйте «Служебный домен» шлюза. Не используйте старый домен без проверки.

### 5. Обновить VITE_API_URL
В `.github/workflows/deploy-frontend.yml` замените временный маркер `https://<NEW_GATEWAY_DOMAIN>` на фактический HTTPS-домен нового шлюза. Не запускайте production deploy, пока маркер не заменён.

### 6. Push в main
После подстановки проверенного домена отправьте изменение в `main`. GitHub Actions публикует только фронтенд в Object Storage; он не создаёт и не развёртывает API Gateway или Cloud Functions.

### 7. Smoke-тест
```sh
curl -i https://<NEW_GATEWAY_DOMAIN>/healthz
```
Ожидается HTTP 200 и JSON от backend. Подставьте реальный домен.

### 8. Проверить фронтенд
Откройте https://smenavkarmane-business.website.yandexcloud.net и выполните жёсткое обновление. Проверьте CORS, вход (если включён), P&L, STEN AI, документы и загрузку файлов.

## Если что-то не работает

- **401/403:** проверьте IAM и право `functions.functionInvoker` для сервисного аккаунта на обеих функциях.
- **502:** проверьте ID, тег `$latest`, статус функций и логи.
- **404:** проверьте точные пути и формат wildcard-маршрутов в спецификации.
- **CORS:** проверьте `ALLOWED_ORIGINS` backend; должен быть разрешён `https://smenavkarmane-business.website.yandexcloud.net`.

## Что не делаем
- Не удаляем старый шлюз.
- Не меняем backend-функцию, расчёты, P&L или MarkItDown-код.
- Не коммитим секреты.
- Не переключаем фронтенд обратно на прямой URL функции.
