Работай на основании фактов. Если у тебя нет доступа к Yandex Cloud Console/CLI или логам, выполни доступную часть аудита в репозитории и перечисли точные действия, которые должен выполнить владелец. Не заявляй, что проверил облако, если доступа не было.

## Приоритет и ограничения

**Приоритет — оживить текущую архитектуру на Yandex Cloud Functions. Миграцию на Cloud.ru не продолжать.**

1. Не создавать новые платные ресурсы без отдельного явного согласования.
2. Не удалять, не пересоздавать и не останавливать существующие функции, API Gateway, базы данных, бакеты, service accounts, сети или секреты.
3. Не переключать production API URL и не менять DNS/production-трафик без отдельного разрешения.
4. Не запускать миграцию БД, не очищать и не перезаписывать данные, не менять схему БД без подтверждённого плана и согласования.
5. GitHub Actions — только проверка кода. Не добавлять автоматический deploy backend, API Gateway, Cloud Functions или MarkItDown. Frontend deploy в Object Storage не расширять.
6. Не публиковать секреты, токены, пароли, connection strings, полные значения env-переменных или чувствительные логи.
7. Сохранять YandexGPT как AI-провайдера; не заменять его на Ollama или другой сервис.
8. Не подменять реальные данные фиктивными. Не трактовать отсутствие данных как ноль.
9. Любые изменения кода делать в отдельной ветке от актуального `main`, с тестами и PR. Не пушить напрямую в `main`, не использовать force-push.
10. Сначала локализовать первопричину. Не «лечить» 502 простым увеличением таймаутов или отключением проверок без доказательств.

## Этап 1 — аудит без изменений

### A. Репозиторий и сборка

1. Проверь актуальную ветку `main`, последние коммиты и рабочее дерево.
2. Изучи backend entrypoint, маршруты, middleware, обработчики ошибок, конфигурацию БД, Object Storage, MarkItDown и YandexGPT.
3. Сверь переменные окружения, которые реально читает код, с документацией и настройками функции. В отчёте указывай только имена переменных и факт наличия/отсутствия, никогда не значения.
4. Запусти доступные проверки: установка зависимостей, lint, typecheck, тесты, build и backend-specific tests. Отдельно отметь, какие проверки реально запущены и какие пропущены.
5. Проверь, что текущий CI не выполняет deploy backend/API Gateway/Cloud Functions/MarkItDown.

### B. Cloud Function

Если доступ к Yandex Cloud есть, только считай и проверь:

- существует ли функция и какая версия действительно активна;
- runtime, entrypoint/handler, архитектура пакета и версия Node.js;
- состояние последней версии, память, timeout и concurrency;
- service account и необходимые роли — без вывода секретов;
- наличие обязательных env-переменных по именам;
- логи вызовов, cold start, ошибки импорта модулей, необработанные исключения и таймауты;
- соответствует ли структура загружаемого архива тому, что ожидает runtime (например, корректность `index.handler` и зависимостей).

Не создавай новую версию функции на этапе аудита.

### C. API Gateway и HTTP

Проверь фактическую конфигурацию Gateway и маршруты backend. Для каждого ключевого маршрута запиши метод, интеграцию, ожидаемый handler и результат. Особое внимание:

- `GET /api/health` или фактический health endpoint (сначала найди реальный маршрут; не придумывай новый);
- `GET /api/analytics/settings`;
- `PUT /api/analytics/settings` — только безопасный тест в изолированном окружении либо тест с неизменяющим запросом, если контракт это позволяет;
- `OPTIONS` preflight;
- auth, CORS, передача заголовков, query string, request body, status codes и timeout.

Не выводи Authorization headers и пользовательские данные. Не делай запросов, которые могут изменить production-данные без согласования.

### D. Зависимости

Проверь отдельно:

- PostgreSQL: статус кластера/хоста, сетевую доступность из функции, доступность pgbouncer/порта, ошибки подключения, TLS, таймауты и наличие схемы/таблиц. Не выводи DSN или пароли.
- Object Storage: доступность нужных бакетов и IAM, не перечисляя чувствительные объекты без необходимости.
- MarkItDown: endpoint, статус функции, timeout, контракт запроса/ответа.
- YandexGPT: наличие конфигурации и обработку ошибок, не раскрывая ключи.

Разделяй: «функция не запускается», «Gateway не вызывает функцию», «функция запускается, но падает на зависимости» и «маршрут работает, но ломается конкретная бизнес-операция».

**Результат этапа 1:** таблица `симптом → доказательство → вероятная причина → способ проверки → риск`, приоритеты P0/P1/P2 и список недостающих доступов. Никаких изменений инфраструктуры.

## Этап 2 — минимальное исправление в репозитории

После локализации причины:

1. Создай отдельную ветку от актуального `main`.
2. Исправь только подтверждённую проблему в коде, конфигурационных шаблонах или документации. Не меняй облачные ресурсы и production API URL.
3. Проверь контракт Cloud Function: handler экспортируется корректно; ошибки обрабатываются; логи не содержат секретов; запросы к зависимостям имеют разумные timeout; отсутствующие данные не маскируются фиктивными значениями.
4. Добавь тест, воспроизводящий исходную ошибку и подтверждающий исправление. Для сетевых зависимостей используй контролируемые моки только в тестах, явно обозначая их как тестовые.
5. Прогони полный доступный CI: tests, lint, typecheck, build, backend validation и security checks.
6. Подготовь PR с причиной, изменениями, результатами проверок, рисками и инструкцией ручного выката/отката. Не запускай deploy.

Если первопричина находится только в настройках Yandex Cloud, не пытайся имитировать её кодовым изменением. Подготовь владельцу конкретный пошаговый план в консоли/CLI, с командами только для чтения на этапе диагностики и отдельным блоком для каждого потенциально изменяющего действия.

## Этап 3 — восстановление и проверка (только после отдельного разрешения владельца)

До любого изменения облачной конфигурации предъяви владельцу:

- доказанную первопричину и источник доказательства;
- точный ресурс и конкретные поля, которые предлагается изменить;
- ожидаемый эффект и возможные побочные эффекты;
- план проверки после изменения;
- способ отката;
- оценку стоимости, если действие может изменить расходы.

После разрешения владельца выполняй только одобренные действия. Не расширяй их объём по собственной инициативе.

### Критерии восстановления

Считай backend восстановленным только после фактических проверок:

1. Активная версия функции успешно запускается и выполняет handler.
2. Gateway маршрутизирует запросы в правильную функцию.
3. Health endpoint (если он существует) возвращает ожидаемый статус.
4. Ключевые read-маршруты возвращают ожидаемые ответы без 5xx.
5. Write-маршруты проверены безопасным тестом и не изменили реальные данные без разрешения.
6. CORS/OPTIONS работает для разрешённого frontend origin.
7. Необходимые зависимости доступны либо ошибки их недоступности корректно обрабатываются.
8. Нет новых утечек секретов и критических ошибок в логах.
9. CI и тесты прошли, а production smoke-test подтверждён реальным результатом.

## Формат итогового отчёта

1. **Статус:** восстановлено / частично восстановлено / заблокировано.
2. **Что подтверждено:** факты, timestamp проверки и ссылки на evidence.
3. **Первопричина:** только если подтверждена; иначе список гипотез отдельно.
4. **Проверки HTTP:** метод, путь, статус, время и безопасное описание ответа.
5. **Проверки функции и зависимостей:** без секретов.
6. **Изменённые файлы, ветка, commit и PR.**
7. **Что не проверено и почему.**
8. **Следующий минимальный шаг владельца.**
9. **Rollback.**

**Запрещено объявлять STEN восстановленным только по успешной сборке, наличию функции или ответу OPTIONS 204. Нужны доказательства успешного выполнения backend и его критических зависимостей.**
